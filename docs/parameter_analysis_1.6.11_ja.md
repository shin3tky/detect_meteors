# v1.6.11: 取りこぼし画像の分析とパラメータ調整

[English](parameter_analysis_1.6.11.md)

状態: 画像ペアの再実行APIと読み取り専用の分析CLIを実装し、レビュー済み。
調整値の提案・保存は未実装。
今回の基盤整理ではリリース番号を更新せず、実行時バージョンは1.6.10を維持する。

## 目的と利用の流れ

目視で流星を確認したのに候補へ入らなかった画像を起点に、取りこぼしの
原因を調べ、その撮影系列に適したパラメータで再処理できるようにする。
既存の差分・Hough方式を完成させる1.xの拡張として実装する。

1. 利用者が目視確認済みの画像と、元の処理条件を指定する。
2. 通常検出と同じ入力画像・直前フレーム・ROI・前処理で判定を再現する。
3. 差分マスク、線分、輪郭、各閾値の通過状況を表示する。
4. 変更量を抑えた複数の調整案と、調整前後の結果を比較する。
5. 選んだ案を別の設定ファイルへ保存し、撮影系列全体を再処理する。
6. 新規候補と既知の流星を確認して、採用する設定を決める。

一枚がcandidateになることと、その画像中の流星を検出できたことは区別する。
複数の飛跡がある場合は、利用者が示した流星領域と検出形状の対応を確認する。

## 現行実装の整理

## 今回実装する基盤

`meteor_core/detectors/hough_analysis.py` に次の型を設ける。

- `ContourMeasurement`: 候補条件を適用する前の輪郭面積と回転矩形。
- `CandidateThresholds`: 再計測せずに変更できる面積・比率・スコアの閾値。
- `CandidateDecision`: 通過した輪郭、面積条件を満たす輪郭の最大比率、不採用理由。
- `HoughAnalysis`: マスク、全体スコア、線分、輪郭計測と元の候補閾値。

`HoughDetector.detect()` は `analyze()` → `evaluate()` → 必要なデバッグ描画を
組み合わせる。分析専用の別アルゴリズムを作らず、通常検出と同じ計測を使う。
メソッドと互換用関数で重複していたHough線分スコアの計算も共通化する。

候補判定は現行の以下の条件を維持する。

```text
ある同一輪郭について:
    area > min_area
    aspect_ratio > min_aspect_ratio
かつ、画像全体について:
    line_score >= min_line_score
```

比率は `max(width, height) / max(min(width, height), 1)`。
幅または高さがゼロの輪郭は判定から外す。返す最大比率も従来どおり面積条件を
満たす輪郭だけから計算する。面積と比率を別々の輪郭から借りて通過させない。

不採用理由のコードは `no_contours`, `min_area`, `invalid_geometry`,
`min_aspect_ratio`, `min_line_score`。これらは判定の障害となった条件であり、
流星が写っていないという分類ではない。ROI外や前処理で消えた流星の原因まで
`no_contours` から断定しない。輪郭側は最初に進めなくなった段階を示し、
画像全体のスコア不足は併記する。

`evaluate()` は元の閾値・画像・計測値を変更しない。`render_debug()` は
非候補でも明示的に呼べるが、通常検出では従来どおり候補だけを描画する。
通常の結果の `extras`、既存のmetricsのキー、進捗形式、プラグイン契約、
既定値は維持する。このAPIは組み込みHough専用で、全検出器に実装を要求しない。

既存の `DetectionContext` がある場合の基盤APIの使用例:

```python
from dataclasses import replace

from meteor_core.detectors.hough_default import HoughDetector

analysis = HoughDetector().analyze(context)
original = analysis.evaluate()
trial = analysis.evaluate(replace(analysis.thresholds, min_aspect_ratio=2.0))
debug_image = analysis.render_debug(original)
```

この例の `2.0` は呼び出し側が指定する試行値であり、推奨値や新しい既定値ではない。
調整案の選定やファイル保存は行わない。

## 実装ステップ1: 明示した画像ペアの再実行API

`meteor_core/analysis.py` に読み取り専用のAPIを追加した。このステップは
ロードマップの「元条件での再現」のうち、CLIから独立した入力の解決と再実行を
対象とする。テスト後のレビューを受けてからCLI接続へ進む。

- `load_reproduction_settings()`: 元の進捗からパラメータとROIを読み込み、
  各値の出所、明示した変更、元条件の情報不足を保持する。
- `reproduce_hough_pair()`: 明示した対象画像と参照画像を既存のローダーで読み、
  組み込みHough検出器の共通APIを使って計測・判定する。
- `HoughReproduction`: 入力ペア、実効設定、ローダー情報、画像寸法、両画像の
  メタデータ、計測結果と判定をメモリ上に保持する。

パラメータは「既定値 → 呼び出し側の `params` → 進捗の `params` →
進捗の `processing_params` → `parameter_overrides`」の順に適用する。
`params` は欠損値の補完にも使い、記録済みの値を暗黙に上書きしない。
進捗に一部の値がなくても読み込めるが、`parameter_sources` と `limitations` に
補完の事実を残す。設定ファイルを進捗ファイルとして渡した場合や、無効な閾値・
ROIは設定エラーにする。組み込みHoughの7パラメータ以外を黙って無視しない。

ROIは記録済みのものを優先する。`roi_polygon` または `use_full_image=True`
による明示的な変更を認め、両方の同時指定はエラーにする。ROIの記録・指定が
なければ全画面を使い、その仮定を残す。適用したROIが画像に全く重ならない場合は
入力エラーにする。ROI座標はローダーが返す画像の座標系を使う。

```python
from meteor_core.analysis import load_reproduction_settings, reproduce_hough_pair

settings = load_reproduction_settings(progress_path="previous_run/progress.json")
replay = reproduce_hough_pair(
    "raw/frame002.ORF",
    "raw/frame001.ORF",
    settings=settings,
)
print(replay.status)
if replay.decision is not None:
    print(replay.decision.is_candidate, replay.decision.rejection_reasons)
```

参照画像を省略すると `status="reference_missing"` となり、対象画像の情報だけを
返す。計測結果と判定は `None` とし、ゼロ画像や近くの別ファイルで代替しない。
同一ファイル（ハードリンクを含む）、読み込み失敗、寸法・dtypeの不一致、
非グレースケール画像は明示的にエラーにする。

ローダーはインスタンス、または名前・設定で指定できる。両方式の同時指定は
エラーにする。通常処理と同じ解決・入力正規化を使い、未知のローダーに
フォールバックしない。未知のローダーのエラー経路にあった、存在しない
`list_loaders()` の呼び出しも、共通処理で `list_available()` に修正した。

このAPIは検出器本体の再実行に限定する。元の進捗だけではローダー設定や
フックの適用を再現したことにはならず、その制約を `limitations` に残す。
フック、auto-params、参照画像の自動選択、候補コピー、進捗更新、レポート保存は
実行しない。調整案を自動生成する機能も、このステップには含まない。

このステップの検証結果:

- APIのテスト14件を追加し、既存分を含む595件が通過。
- 既存RAWの11隣接ペアについて、全画面・ポリゴンROIの計22比較で通常パイプラインと
  判定・スコア・線分・比率・候補のデバッグ画素が一致し、元の進捗も不変。
- 利用者の `P8136507.ORF` と添付進捗では記録済みの条件を読み込み、直前画像がないため
  `reference_missing` を返すことを確認。元の差分判定を再現したとは扱わない。
- Ruffのlint・整形検査とtyの型検査が通過。

## 実装ステップ2: 分析CLI

レビュー済みのAPIを、通常検出とは別の読み取り専用CLI経路に接続する。

```bash
python detect_meteors_cli.py \
  --analyze-image rawfiles/frame002.ORF \
  --reference-image rawfiles/frame001.ORF \
  --analysis-progress previous_run/progress.json
```

`--reference-image` の代わりに `--analysis-sequence DIR` を使うと、明示した
元の撮影系列内で通常処理と同じRAW収集・ファイル名順を使って直前画像を選ぶ。
対象画像の親フォルダー、既定の入力フォルダー、設定の入力フォルダーからは
系列を推測しない。参照画像の選択方法は相互排他とし、先頭画像には参照がない。
対象画像が指定系列に含まれない場合はエラーにする。

ローダー・検出器設定と補完用パラメータは `--config`、元の記録済みパラメータと
ROIは `--analysis-progress` で指定し、入力形式の取り違えを拒否する。
記録済みの値は設定ファイルのパラメータに優先し、明示した検出パラメータの
フラグは記録値に優先する。元の値からの変更は別に表示する。
`--key value`、`--key=value` とargparseが認める一意な省略形のいずれでも
明示した変更として扱う。ROIの変更には `--roi` または `--no-roi` を使い、
両方の同時指定は拒否する。

選んだ画像ペアと参照の選択方法、元の進捗パス、画像寸法、対象のメタデータ、
ローダー名、実効パラメータの出所、ROI、明示的な変更、制約、候補判定、
不採用理由、計測数を表示する。`--verbose` で輪郭と線分端点も表示する。
日英の表示と、新規4オプションのBash/Zsh補完を用意する。

終了コードは、候補の採否にかかわらず計測完了で0、設定・入力・処理エラーで1、
無効なオプションの組み合わせまたは `reference_missing` で2とする。
参照画像がない場合は判定しない。進捗削除や推定処理の前にモードの矛盾を検査し、
分析時の `--auto-params`、`--remove-progress`、`--show-exif`、`--show-npf`、
`--list-sensor-types`、`--debug-image`、`--progress-file` と明示的な `--target` を
拒否する。他の出力・性能設定は通常の処理パイプラインを起動しない。
`--save-diagnostic` による明示的なエラー診断ファイルの要求は既存の動作を維持する。

組み込みHough以外の検出器と、設定されたフックは拒否する。検出器本体だけを
再実行する場合は利用者が `--hooks ""` と明示できる。このステップでは出力先の
作成、候補コピー、進捗更新、調整案の生成、分析レポートの保存は行わない。
詳しくは[オプション一覧](COMMAND_OPTIONS.md)を参照。

このステップの検証結果:

- CLIのテスト19件を追加し、既存分を含む614件が通過。
- 実RAWの `_C140338.ORF` / `_C140337.ORF` で、参照画像の直接指定と
  系列のファイル名順での選択が、ともに終了コード0で同じ判定・計測表示を返した。
- 利用者のRAWと元の進捗では、日本語CLIが `reference_missing` と終了コード2を
  返した。これら3回の別プロセス実行で、空の作業フォルダーは空のまま、
  元の進捗のバイト列も不変だった。
- Ruffのlint・整形検査、ty、Bash/Zsh補完の構文検査が通過。日英の分析メッセージのキーも一致。

## 入力と再現性の設計

分析ジョブの入力は、対象画像、直前画像、実効パラメータ、ROI、ローダー設定、
検出器設定とする。必要なら目視確認した流星の領域も受け取る。
ファイル名順で直前画像を探す場合は、通常検出と同じファイル収集・並び順を使い、
選んだ組をレポートに明示する。明示指定した参照画像を優先する。
撮影系列を特定できなければ直前画像を推測しない。

元の `progress.json` がある場合は、記録された実効パラメータとROIを
再現の基準に使う。明示した上書きは元の値と区別して記録し、再現条件の変更を
表示する。古い進捗は不足フィールドを許容して読み込む。通常の設定ファイルと
進捗ファイルは別の入力形式として扱い、取り違えない。

直前画像がない単画像でもEXIFやプレビュー、背景の参考情報は提示できる。
ただし差分検出の再現は「参照画像不足」とし、架空の背景やゼロ画像で代替して
調整済みと判定しない。対象画像と参照画像の一致、寸法違い、読み込み失敗、
対象領域とROIの不一致は明示的に扱う。

元の処理を再現する際は、ROIの再選択や `--auto-params` の再実行を暗黙に行わない。
既存のフックを使った実行は検出器本体の結果と区別し、対応できないローダーや
検出器を組み込みHoughへ暗黙に置き換えない。

## 次段階: 調整案の作り方

調整はセッション単位で考える。カメラやレンズだけでなく、空の明るさ、雲、
地上光、星の移動、実効解像度、飽和やノイズが異なるため、機材名だけから
普遍的な最適閾値を決めない。撮影地は任意のセッション情報として記録できるが、
背景の影響は実画像の統計も使って評価する。

調整処理は段階を分ける。

1. 計測を固定して面積・比率・スコアを再評価する。閾値の厳密な比較境界を
   考慮し、数値を丸めたために再実行で不採用になる案を出さない。
2. 必要な場合に差分閾値・Hough設定の範囲を限定して探索し、変更するたびに
   計測し直す。ROI・前処理・解像度の変更時も計測値を再利用しない。
3. 対象の流星領域に対応する証拠を確認し、変更量・追加候補数・既知の流星の
   保持状況を並べて案を比較する。領域の指定がなければ、フレーム単位の救済と
   して示し、流星そのものを特定したとは扱わない。

探索には設定可能な範囲・回数上限を設け、計測回数と終了理由を残す。
根拠が不足する場合は、調整案なし・再現できず・追加データが必要、も有効な結果。
単画像の正例だけでは誤検出率を評価できない。比較画像が与えられた場合は、
同じ実効条件で調整前後を処理し、新規候補と失われた既知候補を列挙する。

線分長の合計を流星の確率や単一飛跡の強さとして扱わない。
将来の強スコア救済ルールは、線分と輪郭の対応付け等を検証した上で追加する。
今回のデータに合わせた `2.0` や特定スコアの組み込み、航空機の自動除外、
時間的な隣接だけによる航空機分類の伝播は、この基盤整理には含めない。

## 次段階: レポートと設定の保存

CLIのオプション名は実装時に確定する。機能としては対象画像の分析、参照画像の
指定、元の進捗の読み込み、分析結果の出力先、調整案の設定保存を用意する。
通常検出とは別の実行経路とし、分析しただけで候補をコピーしたり、元の
進捗を更新したりしない。

分析レポートは独立したバージョン付き形式とし、最低限次を保存する。

- 入力ペア、アプリと分析形式のバージョン、画像寸法、使用する実効設定とROI。
- EXIFと利用者指定情報、元の値・推定値・上書きの出所、再現の成否。
- 元の判定、不採用理由、線分と輪郭の証拠、マスクの参照先。
- 各調整案の変更点、再評価結果、探索範囲と未検証事項。
- 比較系列がある場合の候補の増減と、目視確認済み領域との対応。

調整案の保存先は既存の `--config` で読み込める完全な設定形式にする。
元の設定と分析レポートは別に保ち、ローダーや検出器の設定を失わない。
セッション用ROIなど現行 `PipelineConfig` に保存先がない項目については、
既存CLIの指定と整合する保存・再読み込み方法を実装時に追加する。
出力先が入力RAW・元の進捗・元の設定を上書きしないことも検証する。

## 1.6.11の受け入れ条件

- 通常検出の候補集合、スコア、線分、比率、デバッグ描画が従来と一致する。
- 面積・比率の厳密な `>`、スコアの `>=`、ROI、ゼロ寸法の扱いが維持される。
- 目視確認した取りこぼしを元条件で再現し、阻害条件と調整前後の証拠を示せる。
- 再計測が必要な設定変更で、以前の証拠を使い回さない。
- 必要情報の不足を示せ、候補化だけを流星検出の成功と取り違えない。
- 保存した設定で再実行した結果が、調整案の評価と一致する。
- 既存の進捗・設定・検出器プラグインを利用でき、通常処理の副作用を増やさない。
